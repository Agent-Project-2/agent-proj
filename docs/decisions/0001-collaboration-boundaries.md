# ADR 0001 · NPC 도구 경계와 계약 기반 병렬 개발

- 상태: 초안. A의 로컬 문서 작성 승인만 확인했으며 B의 검토·공동 채택은 대기 중이다.
- 날짜: 2026-11-24 KST
- 초안 작성: A (`gimyang9`)와 A의 개발 에이전트. B를 공동 작성자로 등록하지 않는다.
- 기준: PR #29 병합 main `a3e4f2d8569496bee157db3310511072667c6bac`. 이전 검토의 `bb94a13`·`f826761` 이력은 보존한다.
- 관련: #2 협업 운영, #5 공통 계약, #14 NPC 도구, PR #25·#26. 실제 역할 변경 회의록은 아직 확인되지 않았다.

## 배경과 제약

PR #26은 A의 AI·NPC, B의 게임·UI, 공동 기획·계약·통합을 구분했다. 다만 A가 관리하는 NPC 데이터의 MCP 도구까지 B가 구현하고, 대화·도구가 UI 등 상대 기능 완료를 기다리는 일정이다. 두 팀원이 비슷하게 주 15~25시간을 사용할 때 후반 통합과 B의 구현 면적에 위험이 있다.

최초 읽기 검토에서 Ruleset 27976762의 요구 승인 수는 0이었고 PR #26에 정식 승인 기록이 없었다. 이번 이슈 전수 검토에서는 해당 설정이 2026-11-24 20:18:32 KST에 1건으로 변경된 상태를 확인했다. 현재 PR 필수·승인 무효화·quality·squash·linear history·force push·삭제 차단과 우회 대상 없음도 확인했다. 이 에이전트가 설정을 변경하지는 않았다. Projects #3은 A 계정에서 여전히 404, 저장소 연결 보드는 0개로 표시돼 삭제·권한·연결 중 원인을 확정하지 못했다. 따라서 #2 전체를 완료 처리하지 않는다.

## 고려한 대안과 차이

| 대안                          | 장점                                                         | 단점                                                     |
| ----------------------------- | ------------------------------------------------------------ | -------------------------------------------------------- |
| B가 MCP 서버와 모든 도구 구현 | 등록·배포 진입점이 단순함                                    | A의 NPC 모델 변경마다 B와 조율하며 게임·UI 업무도 집중됨 |
| A·B가 별도 MCP 서버 운영      | 담당별 독립성이 높음                                         | 서버·연결·권한·실행 환경을 두 벌 관리해야 함             |
| 공통 서버와 담당별 도구 모듈  | 원본 데이터 담당자가 도구 의미를 관리하고 운영 기반은 공유함 | 등록·권한·이벤트 처리 계약의 공동 검토가 필요함          |

기능을 순차 완성한 뒤 연결하면 초기 Mock 비용은 줄지만 대기·후반 통합 위험이 커진다. 계약과 예시를 먼저 합의하면 화면·판단·도구를 병렬 개발할 수 있지만 실제 연동 검증을 별도로 수행해야 한다.

## 제안과 채택 조건

공통 서버와 담당별 도구 모듈을 제안한다. B는 서버 기반·게임 상태·증거·기록·행동 실행을, A는 NPC 기억·관계 조회·정보 공유와 클라이언트를 구현한다. 메시지는 서버의 권한·수신 조건 검증 및 이벤트 기록 후 NPC 로직에 반영한다. 게임 상태의 실행 권한은 B의 서버에 둔다.

#5에서 노출 범위·대화·행동·오류·이벤트·중복 처리의 최소 계약과 Mock을 합의한다. Mock으로 착수할 조건과 실제 연동 완료 조건을 나눈다. 기술 스택·전송 방식·저장 배치·상세 스키마를 이 문서만으로 확정하지 않는다.

A가 AI·NPC 관련 문서 항목을, B가 게임·UI 관련 항목을 각자 작성하고 상대가 검토한다. 공동 내용도 실제 작성과 검토를 구분한다. 과거 기여는 [기여 기록](../contributions.md)에 별도로 남긴다.

이 초안은 실제 회의록이나 과거 합의 증명이 아니다. B의 검토와 두 사람의 결론·이유·후속 작업을 실제 회의록 또는 연결된 검토 기록으로 확인한 뒤 상태를 확정으로 바꾼다. 공동 내용의 일방 작성·승인·병합을 허용하지 않는다.

## 영향과 외부 반영 대기

아래 채택·외부 반영은 대기 중이다. 승인 1건의 현재 설정 확인과 보드 접근 미확인을 구분하며 문서 수정으로 외부 변경 완료 처리하지 않는다.

- [ ] B가 NPC 도구 분담, 데이터 원본, 문서 작성 영역과 일정의 착수·연동 구분을 검토하고 A와 합의한다.
- [ ] 승인된 담당자가 #14의 A·B 작성 영역, #4·#5·#8·#10·#12·#13·#15·#16의 착수·연동 구분과 #7 세션·#24 시작 화면 책임을 기존 이슈에 반영한다. #9·#11 본문과 #1 종료 기록은 유지한다.
- [ ] 일정 제안 #6·#7 12/02, #8 12/04, #12·#24 12/05, #13 12/07, #20 12/20, #21 12/22와 #18·#21 P1을 공동 검토한다. #20은 12/13 내부 동결·12/20 제출 검증, #21은 12/13 초안·12/22 발표 준비를 구분한다. 이 변경은 아직 원격에 반영하지 않았다.
- [ ] #1의 최초 작성 기여와 향후 공동 유지를 구분하고 미체크 완료 항목의 근거를 확인한다. 이미 종료된 이슈를 자동 재개하지 않는다.
- [ ] #2에서 이미 확인된 승인 1건 등의 설정을 재변경하지 않고 정식 상대 승인·CI가 실제 PR에서 적용되는지 증빙을 확인한다. 새 bypass는 추가하지 않는다.
- [ ] 기존 Projects #3의 존재·접근 권한·연결을 확인한다. 원인 확인 없이 새 보드를 만들지 않는다. 합의된 계정별 Assignees와 보드의 담당·상태·마감·우선순위를 대조한다.
- [ ] 각자가 자신의 계정으로 문서·코드 PR을 작성하고 상대의 정식 승인과 CI를 확인한다. 이 로컬 변경은 커밋·push·PR 게시·설정 변경·병합 승인이 아니다.

작업 중 B의 폴더 정리 PR #27이 main `f826761`로 병합됐다. 로컬 변경을 최신 main에 충돌 없이 옮겼으며 `game/`·`agent/`·`shared/` 구조와 `scripts/` 검사 명령을 유지한다. 이 작업에서 PR #27을 승인하거나 B 브랜치를 수정하지 않았다.

## 이슈 전수 검토와 PRD 개정 영향

일반 이슈는 #1~#21·#24의 22개이며 #1만 종료, 나머지 21개는 열려 있다. 실제 Assignees는 모두 미지정이다. #1·#9·#11의 내용은 유지하고 나머지 19개는 목적·완료 기준·책임·의존성과 필요한 일정을 보완하는 안이다. #9·#11에는 승인 후 담당 계정만 연결한다. 통합·분할·신규 생성·추가 종료는 제안하지 않는다. #1의 미체크 항목은 증빙을 확인하며 기록을 소급 수정하지 않는다.

누락된 서버 실행·세션 생명주기는 #7, 시작·초기화 UI·기본 아트는 #24, 대화 결과의 공개 기록은 #6, 공통 기술 설계·실행·저장 계약은 #5, 실행 환경과 제출 확인은 #18·#20에 명시한다. 실제 기능·테스트 코드를 이번에 구현하지 않는다.

원격 PR #28은 병합 없이 종료됐고 이를 대체한 #29는 2026-11-24 21:03:49 KST에 main `a3e4f2d`로 병합됐다. #29는 B가 PRD를 교안의 0~10절 구조로 재구성한 작업이며 변경 파일은 PRD 한 개(+129/-102)다. 당시 원격 `TodoList.md`는 main과 같은 blob이었으며 PRD 말미의 절 번호 대응표를 검토에 사용했다. 따라서 #3 사건 설계 완료나 이 로컬 역할 개선 반영으로 취급하지 않는다. 사용자의 추가 요청에 따라 B의 0~10절과 3-1절 구조 및 요구사항을 보존한 로컬 통합 초안을 만들었다. 후속 품질 개선에서는 교수님 원본·예시에 맞춰 문체와 페르소나를 다듬고 상세 요구사항을 별도 기술 요구사항 문서로 분리했다. 과거 번호 대응표는 검토 백업에 보존하고 현재 TodoList는 최종 PRD 항목 번호를 참조한다. 이는 원격 PR 채택·승인·병합이 아니다.

#29 이전 기준으로 만든 PRD diff에는 B의 양식 개정도 포함되므로 그 전체를 A의 커밋으로 제출하지 않는다. 현재 후속 diff는 #29 병합 main을 기준으로 하여 B의 기존 양식 개정을 중복 포함하지 않는다. #29는 이미 병합됐으며 승인된 작업 브랜치에 A의 보완 패치를 적용했다. 커밋·push·후속 PR 작성은 아직 별도 승인 대기다. 별도 임시 인덱스로 #29 결과를 기준 삼아 후속 패치를 검증하며 작업 브랜치를 전환하거나 원격 PR을 수정하지 않는다.

과거 PRD의 역할 §10은 현재 §1과 AGENTS, NPC·수사·사건 요구사항 §4~§6은 현재 §4·§7과 [상세 기능·기술 요구사항](../technical-requirements.md), 완성 기준 §12는 현재 §10에서 확인한다. `TodoList.md`는 최종 PRD의 실제 절·항목 번호를 참조한다. 작업 번호·PRD 번호·GitHub 이슈 번호는 서로 구분한다. PR #29는 병합 완료 상태다. 이번 후속 초안의 상대 검토·채택과 혼동하지 않으며 AI의 검토를 GitHub 승인으로 취급하지 않는다. #29의 `a/` 접두사는 실제 작성자 B와 다르지만 기존 기록은 변경하지 않고 이후 B 작업에 `b/`를 사용한다.

## 반영 파일과 검토 파일의 경계

기존 반영 후보 7개 문서에 제품의 상세 요구사항을 분리한 `docs/technical-requirements.md`를 추가하는 안이다. 기술 요구사항 분리와 공동 채택은 검토 대기 상태다. 원격 응답 JSON·PRD 비교 원본·제안 JSON·생성·검증 스크립트·백업은 저장소 밖 `work/`의 검토 자료이고, 사용자용 보고서·패치는 `outputs/`에 둔다. 도구 설치물과 검토 자료를 프로젝트 커밋에 넣지 않는다.

Projects는 저장소 관리자 권한과 별개로 보드 접근 권한·조직 소유권·실제 링크·저장소 연결을 확인한다. B 또는 보드 소유자가 #3의 존재와 A의 접근 권한을 먼저 확인하고 실제 링크를 전달한 뒤 두 사람이 접근·값을 대조하는 안이다. 원인 확인 전 보드를 재생성하거나 권한을 임의 확대하지 않는다. 보드 확인이 막혀도 합의된 이슈와 TodoList·Mock 기반 개발 준비는 진행할 수 있다.

## 확인할 결과와 재검토 조건

- 동일 계약·Mock으로 UI·대화·도구의 독립 착수가 가능하고 실제 연동 테스트가 별도로 확인된다.
- NPC 도구에서도 비허용 조회·불가능한 행동·중복 요청을 거부하며 사건 진실과 게임 상태 권한이 유지된다.
- 완료·담당·마감이 문서·이슈·Projects에서 일치하고 실제 작성·검토 기록을 찾을 수 있다.
- 12/02의 두 NPC 조기 검증이 지연되면 남은 시간과 원인을 공동 검토한다. 최종 NPC 4명·장소 3곳이나 완료 기준은 별도 합의 없이 변경하지 않는다.

## 승인된 로컬 적용

사용자는 최신 main 동기화·작업 브랜치 생성·기존 패치 적용·상태 문구 및 공동 문서 작성 방식 보완·로컬 검증까지만 승인했다. 기존 7개 수정본을 저장소 밖에 백업하고 동일 원격 커밋을 해시로 확인해 `a/2-협업-이슈-정리`에 패치를 적용했다. 공동 문서는 문서별 작성 책임자 지정 또는 항목별 분담 후 상대 검토를 허용한다. 역할·일정·이슈 변경의 팀 간 합의와 실제 외부 반영은 여전히 대기 중이다. 커밋·push·PR·리뷰 요청·Issues·Projects·설정 변경은 하지 않는다.

## 상세 요구사항 참조

제품의 상태·권한·연동 요구사항은 [상세 기능·기술 요구사항](../technical-requirements.md)에서 관리한다. 이 ADR은 협업 구조의 선택 근거와 채택 상태를 기록한다.

교수님 Todo 프롬프트를 반영한 작업 번호는 로컬 확인 단위이며 GitHub 이슈 분할이 아니다. 사용자 승인 전 구현을 시작하지 않고 단계별 결과 확인을 받되, 이미 승인된 병렬 작업을 다른 담당자의 전체 단계 완료 때문에 중단하지 않는다. 이슈 22개 정리안·원격 미반영 상태와 기존 기여 구분은 유지한다.
